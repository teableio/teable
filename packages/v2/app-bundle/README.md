# @teable/v2-app-bundle

Deployable "table app" bundles for the Teable headless runtime. A bundle is a
zip archive that carries a DotTea/TEA structure, optional seed rows, optional
forward SQL migrations, and a checksummed manifest.

```ts
import { v2CoreTokens } from "@teable/v2-core";
import { Lifecycle } from "@teable/v2-di";
import { DotTeaParser } from "@teable/v2-dottea";
import { createHeadlessRuntime } from "@teable/v2-headless-runtime";
import { buildAppBundle, installAppBundle } from "@teable/v2-app-bundle";

const bytes = await buildAppBundle({
  appId: "app_inventory",
  name: "Inventory",
  version: "1.0.0",
  schemaVersion: 1,
  structure: {
    tables: [
      {
        id: "tbl0000000000000001",
        name: "Products",
        fields: [
          { id: "fld0000000000000001", name: "Name", type: "singleLineText", isPrimary: true },
        ],
        views: [{ type: "grid", name: "Grid" }],
      },
    ],
  },
  seed: {
    tbl0000000000000001: [{ fields: { fld0000000000000001: "Widget" } }],
  },
});

const runtime = await createHeadlessRuntime({
  backend: { kind: "pglite", dataDir: "./data" },
});

// The host composition root registers the DotTea parser used by structure import.
runtime.container.register(v2CoreTokens.dotTeaParser, DotTeaParser, {
  lifecycle: Lifecycle.Singleton,
});

const installed = await installAppBundle(runtime, bytes, {
  actorId: "usr_local",
  baseName: "Inventory",
});

console.log(installed.baseId, installed.tables);
await runtime.close();
```

## Bundle layout

```
manifest.json
structure.json
seed/<tableId>.json              # optional
migrations/<schemaVersion>.sql   # optional
```

- `manifest.json`
  - `formatVersion`: currently `1`.
  - `appId`, `name`, `version`, `schemaVersion` (positive integer).
  - `minRuntimeVersion` (optional metadata), `createdAt` (ISO timestamp).
  - `checksums`: sha256 digests for the `structure`, `seed`, and `migrations`
    sections. `buildAppBundle` derives these; callers cannot supply them.
- `structure.json`: a DotTea/TEA structure payload. It is the same file a `.tea`
  file carries, so `ImportDotTeaStructureCommand.createFromBuffer` can parse the
  bundle directly.
- `seed/<tableId>.json`: an array of `{ "fields": { "<fieldId>": value } }`.
  Keys are field ids declared in `structure.json`; the installer remaps them to
  the ids generated by the structure import.
- `migrations/<schemaVersion>.sql`: authored forward SQL for one schema version.
  Multiple statements are allowed; the installer executes them in order inside
  one transaction.

Unknown archive entries are rejected. Entry names must be relative paths with no
`..`, absolute, or backslash segments.

## Checksum format

Section digests are deterministic and independent of zip metadata:

- `structure`: sha256 of the raw `structure.json` bytes.
- `seed` and `migrations`: sha256 of the sorted records
  `"<archive path>\\0<sha256 of file bytes>\\n"` for every file in the section.
  An empty section hashes to sha256 of the empty string.

The install table stores a bundle checksum derived from the three section
digests. Rebuilding identical content stays idempotent; changing content under
the same `version` is rejected.

## Installation semantics

- The first install creates a base (`CreateBaseCommand`), imports the structure,
  writes seed rows, and inserts an `app_bundle_install` row in the data database.
- Reinstalling the same `version` with the same `schemaVersion` and content is a
  no-op that returns the existing base and tables.
- Same `version` with different content is rejected (`install.version_conflict`).
- A lower `schemaVersion` is rejected (`install.schema_downgrade`).
- A higher `schemaVersion` requires `migrations/<version>.sql` for every version
  between the installed and the target version. Migrations run in order inside a
  transaction together with the install-row update.
- Seed rows are written only on the first install. They are a snapshot, not an
  incremental change set.
- Historic migrations on a first install are not executed: `structure.json`
  already describes the target schema.

The install record lives in the data database:

```sql
create table if not exists public.app_bundle_install (
  app_id varchar(255) primary key,
  base_id varchar(255) not null,
  version varchar(128) not null,
  schema_version integer not null,
  checksum varchar(64) not null,
  installed_at timestamptz not null default now()
);
```

The installer requires `v2CoreTokens.dotTeaParser` to be registered by the host
composition root:

```ts
runtime.container.register(v2CoreTokens.dotTeaParser, DotTeaParser, {
  lifecycle: Lifecycle.Singleton,
});
```

`installAppBundle` never mutates the runtime container. When the token is
unregistered it fails with `install.dot_tea_parser_missing` before creating a
base or importing structure, so a missing dependency cannot leave partial state.

Installation is backend-agnostic: it works against a PGlite or PostgreSQL
runtime. The `@teable/v2-headless-cli` `build:bun:pglite` single-file binary is
the simplest local distribution target, since it carries its own PGlite assets.

This package is Node/Bun-only: it uses `node:crypto` and the zip filesystem
layer of `fflate`.

## Not part of this package

- Authentication, permissions, users, and UI.
- Cloud storage, signing, or distribution of bundles.
- Schema diffing: migrations are explicit SQL authored by the app owner.
- Rollback/down migrations.
